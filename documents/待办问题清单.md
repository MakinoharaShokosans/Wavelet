## ✦ 2. 待办议题详细设计与验收指标

### ✅ ISSUE-01: 播放时物理文件丢失防御 (Lazy Check & Graceful Auto-Skip) [已完成]
> **落地状态**：已全链路实现并接入 6 项自动化测试验证（包含单曲缺失、连续级联跳播、全列熔断与 HTTP 404 断链防御，Git Commit: `64e6014`, `9409c8f`）。
- **痛点描述**：
  服务运行期间，用户若在外部直接删除了某首正在播放或等待播放的歌曲：
  - 后端 Direct PCM 硬件直通通过 FFmpeg 打开文件失败抛出 `ENOENT`；
  - Web Audio 模式下前端请求 `/api/stream/:trackId` 返回 404/500；
  - 导致播放器当前音频流彻底断流、界面报红、队列停滞，用户体验中断。
- **解决方案**：
  1. **开流前轻量预检**：在 `PlaybackRouter` 和 `stream.route.ts` 开流前毫秒级执行 `fs.existsSync(track.filePath)`。
  2. **优雅故障分流**：若文件物理丢失：
     - 不触发致命崩溃，记录 Warn 审计日志；
     - 后端向前端下发 WS 事件广播通知 `track:missing`；
     - 前端播放器捕获到缺失状态，Toast 提示 `《xxx》物理文件已丢失，自动跳过`；
     - 队列状态机在 200ms 内**自动优雅滑动播放下一首 (Auto-Skip to Next)**。
- **验收标准**：
  - 播放过程中物理 `rm` 正在播放的曲目，播放器不抛未捕获异常，200ms 内无缝切入下一首；
  - 连续删除队列中后 3 首曲目，切歌能连续跳过并精准落入第 4 首正常歌曲。

### ✅ ISSUE-02: 曲目移动与重命名追踪保活 (Hash-based Move/Rename Tracking) [已完成]
> **落地状态**：已全链路实现四阶段协调同步与零哈希快径机制（Zero-Hash Fast Path），并通过单元测试 4 大场景验证（同目录改名、深层子目录嵌套移动、批量重命名/移动/删除混合、幂等性等均 100% 通过）。
- **痛点描述**：
  用户在 `musics/` 下修改文件名（如 `01.song.flac` -> `01. 歌名.flac`）或新建子文件夹分类（如挪进 `musics/J-Pop/`）：
  - 传统路径比对会判定为：“旧文件不存在 -> 从数据库注销（清空红心、清空播放统计、移出歌单）”；
  - 同时判定“新路径是全新歌曲 -> 重新自愈、重新抽取波形、挂载到未集成歌单”；
  - 导致发烧友的心血标记与歌单分类荡然无存。
- **解决方案**：
  1. **哈希快速比对**：重新扫描时，如果发现某路径不存在，不立即执行物理删除；
  2. **指纹寻回对齐**：对于新发现的音频文件，先计算其 `file_hash`。若在已失联曲目中命中完全相同的哈希：
     - 判定为**路径迁移事件 (Track Path Migration)**；
     - 执行 `UPDATE tracks SET file_path = ?, updated_at = ? WHERE id = ?`；
     - 完整保留该曲目的 ID、心动收藏标记、播放历史、歌单归属以及已抽取的波形缓存！
- **验收标准**：
  - 将一首已打上心动红心、已加入自定义歌单的歌曲重命名并移入深层子目录；
  - 触发曲库扫描后，该歌曲依然保留在原歌单中、红心保持点亮、播放次数不重置。

### ✅ ISSUE-03: 软缺失标记与失联挽救机制 (Soft Missing vs Hard Pruning) [已完成]
> **落地状态**：已全链路实现方案 A（永不自动物理删除，软缺失标记 + 归位无损自动复活 + 前端置灰徽标与用户主导一键清理），通过专属单元测试四大场景（软缺失持久化、自动复活、播放预检联动、主动 Prune 清理）及全量 27 个测试套件（113 项测试全部通过）。
- **痛点描述**：
  用户可能只是不小心把文件移出了目录、或者临时放在了回收站，如果扫描器直接抹除数据库条目，就失去了任何“反悔挽救”的余地。
- **解决方案**：
  1. **数据库扩充**：给 `tracks` 表增设 `is_missing BOOLEAN DEFAULT 0` 列。
  2. **软失效标记**：扫描发现文件物理缺失时，仅标记 `is_missing = 1`。
  3. **UI 视觉表现**：
     - 在歌单列表与卡片上，缺失曲目呈半透明/置灰态，标题旁标注轻量感叹号徽标；
     - 点击时友好提示：`文件不存在，请检查本地路径: ...`；
     - 菜单提供“重新定位物理文件”或“彻底从曲库注销”操作。
  4. **自动复活**：若未来该文件被原样放回，扫描器检测到文件重新存在，自动解除 `is_missing = 0`。
- **验收标准**：
  - 临时挪走歌曲后扫描，歌单中曲目未被剔除，呈现置灰失效态；挪回歌曲再次扫描，自动无损复原。

### ✅ ISSUE-04: 外部存储卸载 / 0 文件防空门熔断保护 (Storage Disconnect Circuit Breaker) [已完成]
> **落地状态**：已在 `musics-syncer.ts` 实现 0 文件防空门熔断保底（若扫描音频数为 0 但数据库中存在存量曲目，立即中断同步以保护全库不被误标记失联，同时在 API 层面支持 `{ force: true }` 逃生舱）。通过专属单元测试四大场景（空门熔断触发、单曲常规删除不误伤、逃生舱跳过、API 响应联动）及全量 28 个测试套件（117 项测试全绿）。
- **痛点描述**：
  若用户的曲库目录被误移走、重命名，或外置挂载点失效时启动服务或触发扫描，`existsSync` 将全部返回 false；扫描器若无防护，会瞬间执行全盘软失效或清空，造成全库置灰。
- **解决方案**：
  1. **0 文件防空门熔断保底**：在执行曲目比对前，若发现扫描物理音频数为 0 但数据库中原本存在该目录曲目，立即熔断终止本次同步；
  2. **全面冻结**：禁止修改数据库，不标记软缺失更不物理删除；
  3. **逃生舱机制**：在 API 及函数入参支持 `{ force: true }`，供管理员在确需清空时显式绕过熔断。
- **验收标准**：
  - 模拟将目录清空或移走，执行 `syncMusicsDirectory`，数据库条目 100% 完好冻结，API 与日志给出熔断警告。

### ✅ ISSUE-05: 拷贝中 / 下载中未完成文件防误伤 (Incomplete File Guard) [已完成]
> **落地状态**：已在 `musics-syncer.ts` 实现临时/下载中文件过滤 (`isIncompleteOrTempFile`) 与写入期尺寸稳定性巡检 (`isFileWritingInProgress`)；在扫描入库前自动对尺寸/时间戳变动或刚创建的 0 字节文件做暂缓入库处理，绝不报致命错误、绝不误入隔离区。通过专属单元测试四大场景（临时后缀过滤、活跃追加动态检测、扫描防误伤隔离区零污染、写入完成自动追引入库）及全量 29 个测试套件（121 项测试全绿）。
- **痛点描述**：
  当用户正在往 `musics/` 复制大体积 192kHz/24bit Hi-Res 母带文件，或浏览器/下载器正在落盘：
  - 文件此时处于增长状态，二进制尾部缺失；
  - 扫描器若过早介入，会触发 FFmpeg 解码失败，自愈流水线可能会误判为“破损不可修复”而将其误移入隔离区。
- **解决方案**：
  1. **临时后缀白名单过滤**：自动排除常见临时后缀：`.tmp`, `.part`, `.crdownload`, `.downloading`, `.~*`, `._*` 等。
  2. **写入锁定与尺寸稳定性巡检**：
     - 对新检测到的音频文件，记录其初始大小；
     - 延迟二次比对 `fs.statSync(filePath).size` 与 `mtime`；
     - 若仍在变化或为新创建 0 字节文件，说明外部进程正在写入，静默推迟到下一次扫描。
- **验收标准**：
  - 模拟一个流式写入过程中的半截 FLAC 文件，扫描器不报致命错误，也不会将其移入隔离区。

- **验收标准**：
  - 放置无内嵌封面的纯净 FLAC 与同目录 `cover.jpg`，扫描后大舞台与卡片无缝展示该封面。

### ✅ ISSUE-08: 歌单幽灵引用与曲目计数校准 (Playlist Count Recalibration) [已完成]
> **落地状态**：已全链路实现原子重算与孤立关联消除引擎并在网关、仓储、自愈守卫全面接入。
> 1. **核心仓储**：在 `PlaylistRepository` 实现 `recalibrateTrackCounts()`，原子级联清理孤立无主关联、普通歌单已软删除幽灵关联、回收歌单中已恢复曲目关联；目录文件夹（Folder）强制归零保底；非目录歌单通过 `INNER JOIN tracks t` 过滤 `COALESCE(t.is_trashed, 0) = 0` 准确重算冗余计数；升级 `updateTrackCount` 保持单歌单高频修改时的计数纯净。
> 2. **自愈与全流程保底**：
>    - `IntegrityGuard.purgeTrackCompletely` 与 `purgeMissingTracks` 彻底销毁曲目时自动触发全量校准；
>    - `musics-syncer.ts` 在全盘就地扫描收尾阶段自动触发全量校准；
>    - `PlaylistRepository.emptyTrash` 清空回收站自动触发全量校准；
>    - `BackupManager.restoreDump` 跨机还原备份后自动触发全量校准；
>    - 网关开放 `POST /api/playlists/recalibrate-counts` 支持前端及运维主动核准。
> 3. **前端状态机联动**：`playlistService` 封装 `recalibrateCounts`，`useLibraryStore` 提供 `recalibratePlaylistCounts` 并与 `fetchPlaylists`、`fetchPlaylistTree`、`refreshStats` 完整联动。
> 4. **质量保障**：新增单元测试 `tests/unit/playlist-recalibration.test.ts`（6 大场景：物理彻底擦除自动校准、移入回收站与恢复计数隔离、批量清理失联曲目重算、目录文件夹强制归零、孤立幽灵关联清理、清空回收站清空计数归零）通过率 100%，全量回归 32 个测试套件（135 项测试）全绿。
- **痛点描述**：
  当某歌曲因物理删除被从 `tracks` 中抹除后，虽然 `playlist_tracks` 依靠外键级联删除了关联记录，但 `playlists.track_count` 冗余计数字段未同步减少，导致侧边栏与歌单详情显示的曲目数虚高。
- **解决方案**：
  1. 在 `PlaylistRepository` 中提供 `recalibrateTrackCounts()`；
  2. 原子清除非法幽灵关联并准确执行 `UPDATE playlists SET track_count = (...) WHERE is_folder = 0`；
  3. 目录文件夹强制 `track_count = 0`；
  4. 在每次曲库同步、单曲擦除、批量清理失联曲目、清空回收站后自动触发校准。
- **验收标准**：
  - 某歌单原本有 5 首歌，在外部物理删除 2 首后扫描曲库，该歌单的曲目统计即刻准确更新为 3 首。

### ⚪ ISSUE-09: 实时文件系统变动监听 (FS Watcher / inotify)
- **痛点描述**：
  用户在文件夹增删歌曲后，必须手动打开设置点击“扫描”或重启服务，缺乏即时反馈。
- **解决方案**：
  1. 后端启动轻量级 `chokidar` 或 Node 原生递归 `fs.watch` 监听 `musics/` 目录；
  2. 针对外部新增（`add`）、删除（`unlink`）、重命名事件加入 500ms 防抖批处理；
  3. 自动静默触发局部增量同步，并通过 WebSocket 广播 `library:updated` 给前端实时刷新。
- **验收标准**：
  - 在运行状态下将新歌拖入 `musics/`，前端在 1 秒内无刷新自动浮现新歌曲卡片。

## ✦ 3. 落地推进建议路线 (Roadmap Recommendation)

- **第一阶段（最关键的基础安全防卫）**：
  - 优先落地 **ISSUE-01（播放中丢失自动切歌防卡死）** 与 **ISSUE-04（批量失联防灾熔断）**，确保系统在任何物理意外下绝对不崩溃、不毁库。
- **第二阶段（发烧级数据连续性保障）**：
  - 落地 **ISSUE-02（基于 Hash 的移动重命名追踪保活）** 与 **ISSUE-03（软失效标记）**，彻底消除发烧友精心整理歌单时的心智负担。
- **第三阶段（自动化与细节打磨）**：
  - 落地 **ISSUE-05 ~ ISSUE-08**（临时文件过滤、标签增量刷新、外挂歌词封面嗅探与计数校准）。
