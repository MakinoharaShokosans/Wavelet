# 📋 Wavelet 曲库一致性与本地文件生命周期待办清单 (TODO & Backlog)

> **设计基石**：Wavelet 确立以项目根目录 `musics/` 作为本地音频资产的**单一真理来源 (Single Source of Truth)**，SQLite 数据库仅作为毫秒级索引与元数据关联中枢。  
> 当用户在操作系统文件管理器或终端中**直接新增、移动、改名、编辑、删除**物理文件时，系统必须具备极高韧性的一致性自愈、防卡顿与防灾保护能力。

## ✦ 2. 待办议题详细设计与验收指标

### 🟢 ISSUE-01: 播放时物理文件丢失防御 (Lazy Check & Graceful Auto-Skip) [已实现]
- **痛点描述**：
  服务运行期间，用户若在外部直接删除了某首正在播放或等待播放的歌曲：
  - 后端 Direct PCM 硬件直通通过 FFmpeg 打开文件失败抛出 `ENOENT`；
  - Web Audio 模式下前端请求 `/api/stream/:trackId` 返回 404/500；
  - 导致播放器当前音频流彻底断流、界面报红、队列停滞，用户体验中断。
- **解决方案**：
  1. **开流前轻量预检**：在 `PlaybackRouter` 和 `stream.route.ts` 开流前毫秒级执行 `fs.existsSync(track.filePath)`。
  2. **优雅故障分流**：若文件物理丢失：
     - 不触发致命崩溃，记录 Warn 审计日志；
     - 后端向前端下发 WS 事件广播通知 `track:missing`；
     - 前端播放器捕获到缺失状态，Toast 提示 `《xxx》物理文件已丢失，自动跳过`；
     - 队列状态机在 200ms 内**自动优雅滑动播放下一首 (Auto-Skip to Next)**。
- **验收标准**：
  - 播放过程中物理 `rm` 正在播放的曲目，播放器不抛未捕获异常，200ms 内无缝切入下一首；
  - 连续删除队列中后 3 首曲目，切歌能连续跳过并精准落入第 4 首正常歌曲。

### 🔴 ISSUE-02: 曲目移动与重命名追踪保活 (Hash-based Move/Rename Tracking)
- **痛点描述**：
  用户在 `musics/` 下修改文件名（如 `01.song.flac` -> `01. 歌名.flac`）或新建子文件夹分类（如挪进 `musics/J-Pop/`）：
  - 传统路径比对会判定为：“旧文件不存在 -> 从数据库注销（清空红心、清空播放统计、移出歌单）”；
  - 同时判定“新路径是全新歌曲 -> 重新自愈、重新抽取波形、挂载到未集成歌单”；
  - 导致发烧友的心血标记与歌单分类荡然无存。
- **解决方案**：
  1. **哈希快速比对**：重新扫描时，如果发现某路径不存在，不立即执行物理删除；
  2. **指纹寻回对齐**：对于新发现的音频文件，先计算其 `file_hash`。若在已失联曲目中命中完全相同的哈希：
     - 判定为**路径迁移事件 (Track Path Migration)**；
     - 执行 `UPDATE tracks SET file_path = ?, updated_at = ? WHERE id = ?`；
     - 完整保留该曲目的 ID、心动收藏标记、播放历史、歌单归属以及已抽取的波形缓存！
- **验收标准**：
  - 将一首已打上心动红心、已加入自定义歌单的歌曲重命名并移入深层子目录；
  - 触发曲库扫描后，该歌曲依然保留在原歌单中、红心保持点亮、播放次数不重置。

### 🟡 ISSUE-03: 软缺失标记与失联挽救机制 (Soft Missing vs Hard Pruning)
- **痛点描述**：
  用户可能只是不小心把文件移出了目录、或者临时放在了回收站，如果扫描器直接抹除数据库条目，就失去了任何“反悔挽救”的余地。
- **解决方案**：
  1. **数据库扩充**：给 `tracks` 表增设 `is_missing BOOLEAN DEFAULT 0` 列。
  2. **软失效标记**：扫描发现文件物理缺失时，仅标记 `is_missing = 1`。
  3. **UI 视觉表现**：
     - 在歌单列表与卡片上，缺失曲目呈半透明/置灰态，标题旁标注轻量感叹号徽标；
     - 点击时友好提示：`文件不存在，请检查本地路径: ...`；
     - 菜单提供“重新定位物理文件”或“彻底从曲库注销”操作。
  4. **自动复活**：若未来该文件被原样放回，扫描器检测到文件重新存在，自动解除 `is_missing = 0`。
- **验收标准**：
  - 临时挪走歌曲后扫描，歌单中曲目未被剔除，呈现置灰失效态；挪回歌曲再次扫描，自动无损复原。

### 🟡 ISSUE-04: 外部存储卸载 / 大规模失联熔断保护 (Storage Disconnect Circuit Breaker)
- **痛点描述**：
  若用户的曲库目录位于外置移动固态硬盘（USB SSD）、NAS 网络挂载卷，或由符号链接指向外部存储：
  - 当硬盘未插、网络掉线或挂载点失效时启动服务或触发扫描，`existsSync` 将全部返回 false；
  - 扫描器若无防护，会瞬间执行全盘清空，直接毁灭几十 GB 曲库的全部元数据与心动数据。
- **解决方案**：
  1. **目录非空基线检查**：在执行孤立清理前，先核查 `musics/` 根目录自身是否真实可读且包含文件。
  2. **安全熔断阈值 (Circuit Breaker)**：
     - 若单次扫描发现丢失比例超过 **30%** 且丢失数量 **>= 5 首**；
     - 或历史曲库不为空但当前目录下未扫描到任何音频；
     - **强制触发紧急熔断**：全面冻结清理逻辑，禁止修改数据库；
     - 输出红色警报日志并在前端弹出模态告警：`检测到大量音频文件同时失联，已触发防灾熔断保护，请检查存储设备是否已正确挂载！`。
- **验收标准**：
  - 模拟将包含 50 首歌曲的目录重命名或移走，执行 `syncMusicsDirectory`，数据库条目 100% 完好冻结，控制台与 API 给出熔断警告。

### 🟡 ISSUE-05: 拷贝中 / 下载中未完成文件防误伤 (Incomplete File Guard)
- **痛点描述**：
  当用户正在往 `musics/` 复制大体积 192kHz/24bit Hi-Res 母带文件，或浏览器/下载器正在落盘：
  - 文件此时处于增长状态，二进制尾部缺失；
  - 扫描器若过早介入，会触发 FFmpeg 解码失败，自愈流水线可能会误判为“破损不可修复”而将其误移入隔离区。
- **解决方案**：
  1. **临时后缀白名单过滤**：自动排除常见临时后缀：`.tmp`, `.part`, `.crdownload`, `.downloading`, `.~*`。
  2. **写入锁定与尺寸稳定性巡检**：
     - 对新检测到的音频文件，记录其初始大小；
     - 延迟 200ms 二次比对 `fs.statSync(filePath).size` 与 `mtime`；
     - 若仍在变化，说明外部进程正在写入，静默推迟到下一次扫描。
- **验收标准**：
  - 模拟一个流式写入过程中的半截 FLAC 文件，扫描器不报致命错误，也不会将其移入隔离区。

---

### 🟢 ISSUE-06: 外部标签与封面变更增量同步 (`mtime` Incremental Resync)
- **痛点描述**：
  发烧友常使用外部专业打标工具（如 Mp3tag、Picard）批量重命名专辑、修改流派（Genre）或嵌入高清封面。由于文件物理路径未变，现有扫描器默认跳过已有路径，导致修改无法呈现在播放器中。
- **解决方案**：
  1. 扫描时比对文件的物理 `stat.mtimeMs` 与数据库记录的 `updated_at`；
  2. 若 `mtimeMs > updated_at`：
     - 判定外部发生了文件写入或元数据变更；
     - 触发增量刷新：重新解析 Vorbis 标签与内嵌封面、重新计算整轨波形并更新数据库。
- **验收标准**：
  - 通过外部工具修改一首歌曲的内嵌封面或标题，重新执行扫描后，Wavelet 界面立即更新为新封面与新标题。

---

### 🟢 ISSUE-07: 外挂伴随歌词与同级封面探测 (Sidecar Files)
- **痛点描述**：
  传统发烧友习惯将 LRC 歌词以独立文件存放（如 `海の見える街.flac` + `海の見える街.lrc`），以及在专辑目录下放置 `cover.jpg` 或 `folder.png`。
- **解决方案**：
  1. **外挂歌词**：若音频内未嵌 LRC，自动在同目录嗅探 `${basename}.lrc`，自动读取入库并标记 `hasEmbeddedLyrics = true`。
  2. **外挂封面**：若音频无内嵌封面，自动在同级目录嗅探 `cover.jpg`, `cover.png`, `folder.jpg`, `front.jpg` 作为专辑封面。
- **验收标准**：
  - 放置无内嵌封面的纯净 FLAC 与同目录 `cover.jpg`，扫描后大舞台与卡片无缝展示该封面。

---

### 🟢 ISSUE-08: 歌单幽灵引用与曲目计数校准 (Playlist Count Recalibration)
- **痛点描述**：
  当某歌曲因物理删除被从 `tracks` 中抹除后，虽然 `playlist_tracks` 依靠外键级联删除了关联记录，但 `playlists.track_count` 冗余计数字段未同步减少，导致侧边栏与歌单详情显示的曲目数虚高。
- **解决方案**：
  1. 在 `PlaylistRepository` 中提供 `recalibrateTrackCounts()`；
  2. 执行 `UPDATE playlists SET track_count = (SELECT COUNT(*) FROM playlist_tracks WHERE playlist_id = playlists.id)`；
  3. 在每次曲库同步或删除曲目后自动触发校准。
- **验收标准**：
  - 某歌单原本有 5 首歌，在外部物理删除 2 首后扫描曲库，该歌单的曲目统计即刻准确更新为 3 首。

---

### ⚪ ISSUE-09: 实时文件系统变动监听 (FS Watcher / inotify)
- **痛点描述**：
  用户在文件夹增删歌曲后，必须手动打开设置点击“扫描”或重启服务，缺乏即时反馈。
- **解决方案**：
  1. 后端启动轻量级 `chokidar` 或 Node 原生递归 `fs.watch` 监听 `musics/` 目录；
  2. 针对外部新增（`add`）、删除（`unlink`）、重命名事件加入 500ms 防抖批处理；
  3. 自动静默触发局部增量同步，并通过 WebSocket 广播 `library:updated` 给前端实时刷新。
- **验收标准**：
  - 在运行状态下将新歌拖入 `musics/`，前端在 1 秒内无刷新自动浮现新歌曲卡片。

## ✦ 3. 落地推进建议路线 (Roadmap Recommendation)

- **第一阶段（最关键的基础安全防卫）**：
  - 优先落地 **ISSUE-01（播放中丢失自动切歌防卡死）** 与 **ISSUE-04（批量失联防灾熔断）**，确保系统在任何物理意外下绝对不崩溃、不毁库。
- **第二阶段（发烧级数据连续性保障）**：
  - 落地 **ISSUE-02（基于 Hash 的移动重命名追踪保活）** 与 **ISSUE-03（软失效标记）**，彻底消除发烧友精心整理歌单时的心智负担。
- **第三阶段（自动化与细节打磨）**：
  - 落地 **ISSUE-05 ~ ISSUE-08**（临时文件过滤、标签增量刷新、外挂歌词封面嗅探与计数校准）。
