## T1 · ISSUE-10 本地网关鉴权加固

### 现状（已核实）
- `GET /api/auth/token` 无任何限制即可取令牌（`settings.route.ts`）。
- **WebSocket 完全未鉴权**：前端把 `?token=` 带上了，但 `/ws/live` 不在 `/api` 下，`sessionGuard` 直接放行，服务端也没校验（`server.ts`、`websocket.ts:61`）。
- `onResponse` 日志记录完整 `request.url`，含 `?token=...`，**令牌会落入日志文件**。
- 令牌比较用 `!==`，非常量时间。
- `.env` 支持 `HOST=0.0.0.0`，此时整个网关暴露给局域网且令牌可被任何人领取。

### 威胁模型（写进 `后端架构设计.md`，说清边界）
防御对象：DNS rebinding 的恶意网页、局域网内其他主机（host≠回环时）、日志泄露。
**不防御**：同一用户下的本机恶意进程（能读进程内存、伪造 Origin，无法靠 HTTP 层挡住）。文档里要明确写出，不要夸大。

### 方案
1. **Host 白名单（防 DNS rebinding）**：全局 `onRequest` 钩子（含 WS 升级）校验 `Host` 头 ∈ {`127.0.0.1:<port>`、`localhost:<port>`、`[::1]:<port>`、配置的 host:port}；否则 `421`。
2. **Origin 校验**：请求带 `Origin` 时，必须 ∈ `corsOrigins` ∪ 同源，否则 `403`。适用于 `/api/auth/token` 与 `/ws/live`。无 `Origin`（CLI/curl/同源导航）放行。
3. **WS 鉴权**：握手时校验 `?token=`（常量时间），失败 `socket.close(4401)`；同时做 Origin 校验。
4. **令牌比较**：`crypto.timingSafeEqual`（先比长度）。
5. **Query token 收窄**：仅 `/api/stream/*`、`/api/tracks/:id/cover`、`/api/playlists/:id/cover`、`/ws/live` 接受 `?token=`；其他 `/api` 路由只认请求头。
6. **日志脱敏**：`onResponse/onError` 日志中的 URL 去掉 `token` 查询参数（写一个 `redactUrl()`，并加单测）。
7. **非回环监听强制口令**：若 `config.server.host` 不是回环地址，启动时要求环境变量 `WAVELET_ACCESS_KEY`，缺失则**拒绝启动**并给出明确报错；`/api/auth/token` 此时要求 `x-wavelet-access-key` 头匹配才发令牌。前端：令牌 401 且需口令时弹最小输入层（可先用 `prompt` 级别 UI，不需精致）。
8. **CLI 兼容**：`bin/wavelet` 通过 curl 取令牌（无 Origin，回环 Host），保持可用；若设置了 `WAVELET_ACCESS_KEY`，CLI 自动带上该头。

### 涉及文件
`gateway/server.ts`、`gateway/middleware/session-guard.ts`（可新增 `host-origin-guard.ts`）、`gateway/routes/settings.route.ts`、`bootstrap/bootstrap-manager.ts`（启动期口令检查）、`config/`、`frontend/src/services/websocket.ts`、`frontend/src/services/apiClient.ts`、`bin/wavelet`。

### 验收（`tests/integration/gateway.test.ts` 或新增 `gateway-security.test.ts`）
- 伪造 `Host: evil.com` → 421；`Origin: http://evil.com` 取令牌 → 403。
- 无令牌连 WS → 关闭码 4401；带正确令牌 → 正常收到广播。
- 令牌不出现在日志输出（捕获 pino 输出断言）。
- 非回环 host 且无 `WAVELET_ACCESS_KEY` → `startServer` 抛错。
- 原有网关集成测试全部保持通过。

### 坑
- vite dev 代理 `changeOrigin: true` 会把 Host 改写成目标；开发态 Origin 为 `127.0.0.1:5173` 已在 `corsOrigins`，注意别误杀开发流程。
- IPv6 `[::1]` 的 Host 解析；端口缺省情形。

## T4 · ISSUE-11 路径沙箱与曲库根目录模型（泳道 B 第 1 步）

### 现状（已核实，含一个回归）
- 上一轮加的沙箱只允许 `libraryDir / cacheDir / dataDir`。但 `wavelet import ~/Music`（`POST /api/import/directory`）是**原地索引任意目录**，这些曲目现在**流播放返回 403、purge 也被拦**。
- 更早就存在的问题：启动同步 `partitionDbTracks` 会 `trackRepo.delete` **所有不在 `libraryDir` 下的曲目**，所以目录导入的曲目下次启动就被清掉。即"导入根"没有被持久化。
- `isPathInsideDir` 用 `relative.startsWith('..')`：误判 `..foo.flac` 等合法文件名；且**不解析符号链接**，库内指向库外的软链可绕过沙箱。
- `integrity-guard.ts` 依赖 `musics-syncer.ts`（工具函数放错了位置），形成不合理依赖。

### 方案：显式的"曲库根 (library roots)"模型
1. **新建 `library/path-guard.ts`**（纯函数，无 DB 依赖）：
   - `isPathInsideDir(file, dir, opts?)`：两侧先 `path.resolve`，再 `realpath`（文件不存在则对"最近存在的祖先"做 realpath 再拼回）；判定用 `rel === '..' || rel.startsWith('..' + path.sep) || path.isAbsolute(rel)` 为"外部"；`rel === ''` 视作目录自身，默认非"内部"。
   - `isPathInsideAnyRoot(file, roots)`。
2. **迁移 `007_library_roots`**：表 `library_roots(path TEXT PRIMARY KEY, kind TEXT NOT NULL, created_at INTEGER NOT NULL)`，`kind ∈ {'primary','imported'}`。`libraryDir` 作为隐式 `primary` 根（启动时 upsert）。
3. **`POST /api/import/directory`**：校验目录存在且为目录 → **登记为 `imported` 根**（realpath 后存储）→ 再索引。需拒绝把系统敏感目录登记为根：至少拒绝 `/`、`/etc`、`/proc`、`/sys`、`/dev`、`/root`、`~/.ssh`、`dataDir` 本身及其祖先（黑名单做成可测试的 `assertRootRegistrable()`）。
4. **启动同步**：对所有根逐一扫描；`partitionDbTracks` 改为"**不在任何根内的曲目不再物理/逻辑删除，而是软缺失标记**"（沿用 ISSUE-03 的 `is_missing`），删除交给用户主动 prune。若现有测试断言旧的"自动删除"，改测试并在待办清单说明语义变化。
5. **沙箱统一入口**：流播放、purge、直通播放均用 `isPathInsideAnyRoot(path, [...roots, cacheDir/healed])`。注意**不再放行整个 `dataDir`**（`dataDir` 含数据库、日志、隔离区，放行等于允许读取 `wavelet.db`），只放行 `cacheDir/healed`。
6. **根的管理 API**（最小集）：`GET /api/import/roots`、`DELETE /api/import/roots`（移除根只取消登记，该根下曲目标记为软缺失，**不删文件**）。
7. 拆分依赖：`integrity-guard.ts`、`stream.route.ts`、`direct-pcm-player.ts` 全部改为从 `path-guard.ts` 引用；`musics-syncer.ts` 不再导出 `isPathInsideDir`（保留 re-export 一个版本以免外部引用断裂，随后删）。

### 验收（`tests/unit/path-guard.test.ts`、`tests/unit/library-roots.test.ts`、更新 `tests/integration/gateway.test.ts`）
- `..foo.flac` 在库内 → 内部；`/musics2/a.flac` 对根 `/musics` → 外部；软链指向库外 → 外部；库根本身是软链 → 正常识别。
- 目录导入 → 重启（重新 `syncMusicsDirectory`）后曲目仍在、可流播放（200/206）。
- 库外随意路径的曲目：流播放 403、purge 不删文件。
- 移除根 → 曲目软缺失、文件仍在盘上。
- 请求 `dataDir/wavelet.db` 对应曲目（构造 filePath 指向它）→ 403。

### 坑
- `realpath` 对不存在文件抛错（purge 时文件可能已不存在），要有祖先回退。
- Windows 盘符/大小写不在本项目范围，但别写死 `/` 分隔符。
- 迁移要幂等、不碰旧数据。

## T5 · ISSUE-12 自愈缓存模块化与一致性（泳道 B 第 2 步）

### 现状（已核实）
`resolvePlayableAudioPath` 每次播放都 `readdirSync(healed)` 按前缀找文件；自愈文件先写 `cache/temp/` 再 `copyFileSync`，temp 副本残留；原文件被刷新/修复为健康后缓存不会失效；在本次修复之前就已是 `repaired` 的曲目没有缓存（播放仍走原文件）；恢复备份后同理。

### 方案
1. **新建 `library/healed-cache.ts`**，把 `resolvePlayableAudioPath` 迁入并导出：
   - 确定性路径 `cache/healed/<trackId><原文件扩展名>`（容器不变，MIME 判定依赖扩展名），**去掉 `readdirSync`**。
   - `persist(trackId, srcTempPath, origExt)`：先写 `*.tmp` 再 `rename` 原子落位；成功后**删除** temp 源文件（用 rename 的话直接就是移动）。
   - `invalidate(trackId)`、`has(trackId)`、`resolvePlayablePath(track)`（`repaired` 且缓存存在才返回缓存，否则 `track.filePath`）。
2. **失效与重建**：`POST /api/tracks/:id/refresh`、增量重同步（`resyncMetadata`）中，文件哈希变化时：重新诊断 → 若仍有损坏则重新自愈并重建缓存，若已健康则 `healthyStatus` 改回健康并 `invalidate`。
3. **回填**：同步流程里，对 `healthyStatus==='repaired'` 但缓存缺失的曲目，**限量**（如每次启动最多 20 首，避免拖慢冷启动）执行"诊断 → 自愈 → 落缓存"；其余留到 refresh 或下次启动。
4. 自愈失败（致命损坏）不影响现有隔离区逻辑。
5. 缓存**不进备份**（可由原文件再生），在 `备份` 文档中写明；还原后靠回填恢复。
6. 所有调用点（`stream.route.ts`、`direct-pcm-player.ts`、`integrity-guard.ts`、`musics-syncer.ts`）切到新模块。

### 验收（扩展 `tests/unit/healers.test.ts` 或新增 `tests/unit/healed-cache.test.ts`、`tests/integration/pipeline.test.ts`）
- 构造损坏样本入库 → `cache/healed/<id>.flac` 存在、temp 无残留；流接口返回的是修复后的字节（长度/头部校验）。
- 删除缓存后回填可重建；purge 曲目后缓存被清；refresh 在原文件被换成健康文件后缓存失效且状态改回。
- 断言播放解析路径时不调用 `readdirSync`（可通过 spy）。

## T3 · ISSUE-13 哈希流式化（泳道 B 第 3 步）

### 现状（已核实）
`computeFileHash` 用 `fs.readFileSync` 整文件入内存再 SHA-256；调用点：`musics-syncer.ts`（入库、迁移检测、增量重同步共 3 处）、`tracks.route.ts` refresh、`flac-standardizer.ts`。192kHz/24bit 的 FLAC 可达数百 MB，期间事件循环被阻塞，网关与 WS 无响应、峰值内存高。

### 方案
1. **保持算法不变（SHA-256 全文件）**，输出必须与旧实现**逐字节一致**：`trackId = trk_<hash前16位>`、`file_hash UNIQUE`、波形/封面缓存键、备份都依赖它，**不做迁移、不换算法、不改成抽样哈希**。
2. 新增 `computeFileHashAsync(filePath, { signal? })`：`createReadStream`（`highWaterMark` 1 MiB）+ `crypto.createHash` 流式更新，返回 `Promise<string>`。
3. 全部调用点改 `await computeFileHashAsync`。同步版保留一个版本并标 `@deprecated`（测试可能在用），确认无引用后删除。
4. **有界并发**：同步/导入循环仍顺序处理文件（保持进度广播顺序与幂等），但哈希读取不阻塞事件循环；不要引入无界 `Promise.all`。
5. 零哈希快径（路径+mtime+size 未变不重算）保持不变，不要破坏。
6. 顺手：`MIME`/stream 等处如有其他 `readFileSync` 读整音频文件的，一并登记到清单（不强制本任务修）。

### 验收
- `tests/unit/` 新增：对同一样本，新旧实现哈希相等；空文件、不存在文件的错误行为与旧版一致（或明确记录差异）。
- `tests/perf/` 新增：生成 ~200 MB 临时文件，用 `perf_hooks.monitorEventLoopDelay` 计算哈希期间最大延迟，断言 `max < 100ms`（阈值可调但需有依据）；旧同步版作为对照只在注释里说明，不进断言。
- 既有 `musics-library`、`soft-missing`、`filename-title-sync` 等测试全绿。

## T2 · ISSUE-14 手动编辑元数据防覆盖（泳道 B 第 4 步，最后做）

### 现状（已核实）
smart/filename 模式下，每次启动与每次增量同步都按文件名重写 `title/artist`（`musics-syncer.ts` 快径分支，另有 `tracks.route.ts` refresh）。用户在编辑弹窗里的修改只写数据库，**下次启动即被覆盖**。

### 方案：字段级"手动锁"，**不写回音频文件标签**
（写标签会改动母带文件，违背项目"母带物理安全第一"原则，明确否决。）
1. **迁移 `008_track_field_locks`**：`tracks` 加 `title_locked BOOLEAN DEFAULT 0`、`artist_locked BOOLEAN DEFAULT 0`（`album` 本就不由文件名派生，无需锁）。
2. 共享类型 `packages/shared/src/types/track.ts` 增加 `titleLocked?`、`artistLocked?`；`TrackRepository` 的 `update/行映射` 同步支持。
3. `PATCH /api/tracks/:id`：白名单字段中，`title` / `artist` 被显式提交且与当前值不同 → 对应锁置 1。
4. **所有"从文件名派生并覆盖"的位置统一加判断**（`musics-syncer.ts` 快径、迁移分支、`tracks.route.ts` refresh、`resyncMetadata`）：锁定字段**跳过**。抽成一个 `applyFilenameDerivedFields(track, parsed, mode)` 纯函数集中处理，避免漏点。
5. 新接口 `POST /api/tracks/:id/reset-metadata`，body `{ fields: ('title'|'artist')[] }`：解锁并按当前文件名重新派生。
6. 前端最小改动（`TrackEditModal.tsx`）：被锁字段旁显示"已手动锁定"和"恢复为文件名"按钮，调用上面接口。遵守 SvgIcons 规范与 Biome a11y 规则。
7. 迁移后的存量数据全部为未锁定（旧的手改已丢失，无法找回，在待办清单里注明）。

### 验收（更新 `tests/unit/filename-title-sync.test.ts`，新增 `tests/unit/track-field-locks.test.ts`）
- 手改标题 → 再跑 `syncMusicsDirectory` → 标题保持不变，文件名派生的 artist（未锁）照常同步。
- 改文件名后重新同步：被锁字段不变；`reset-metadata` 后恢复为新文件名派生值。
- 提交与当前值相同的标题 → 不锁。
- 备份导出/导入往返后锁状态保留（DB 整库拷贝，需验证）。
